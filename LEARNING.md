## 2026-09-17 — WP-00 Stage 7

- Finding: plain `git status --porcelain` (no `--ignored` flag) already omits ignored paths entirely, so `.aws-sam/`, `node_modules/`, and `.tools/` never appear even as `??` lines. `verify-gate-a`'s "no tracked changes" assertion only needs to reject any line that is not a bare `??` (i.e. any tracked-file modification); it does not need to special-case known build-artifact directories.
- Decision: `verify-gate-a` composes the existing `Invoke-Stage*`/`Invoke-OpenApiCheck` functions in sequence rather than re-implementing any check, and uses `Test-RequiredVersions` (which throws on mismatch) rather than `Show-Versions` (which only prints and never fails) for its version gate.
- Decision: `verify-clean-clone` cannot verify a checkout is genuinely a fresh clone from within the script itself; it instead rejects a checkout that is already dirty at start, which is the verifiable proxy the WP-00 spec's "reject an already dirty checkout as evidence" wording asks for. Actual freshness is an operator/evidence-collection responsibility (running the command from a real fresh clone), not something the script can prove.
- Finding: a pre-push audit of the working tree against the WP-00 spec's required skeleton (done before the first commit, since nothing had been committed through Stages 1-7) found 7 missing entries that earlier stage approvals had not caught: root `AGENTS.md`; top-level `workflows/`, `policies/`, `guidance/` boundary directories; `web/src/pages/` and `web/src/components/`; and `tests/live/`. All were added as either a pointer file (`AGENTS.md` → `CLAUDE.md`, per explicit user decision to avoid duplicated/drifting instructions) or one-line ownership/reservation markers matching the existing `services/*/README.md` convention. Future stage reviews should diff the actual filesystem against the spec's required-skeleton tree explicitly, not just trust that prior stage sign-offs covered it.
- Finding: the first real Windows clean-clone evidence run (Stage 7) caught a genuine cross-platform bug the original development machine could never surface: Stage 2's `.gitattributes` only forced `eol=lf` for a narrow allowlist (root config, `scripts/**`, `web/**`), missing `contracts/openapi.yaml`, `services/**`, `tests/**`, `docs/**`, `infra/**`, and other repository-controlled text. On a fresh Windows clone, Git's default `core.autocrlf` converted `contracts/openapi.yaml` to CRLF, and `tests/contracts/openapi-contract.test.mjs`'s raw-text regex match (`\n`-only) failed against it. Fixed by broadening `.gitattributes` to force `eol=lf` across all repository-controlled text trees; verified no file's actual committed content needed changing (everything was already LF at the source, this was a checkout-normalization gap only). This is exactly the class of defect cross-platform Gate A evidence exists to catch before merge.
- Finding: `sam validate --template-file ...` fails with "AWS Region was not found" on a host with no `~/.aws/config` or `AWS_DEFAULT_REGION` at all, even though it performs no real AWS calls for a local structural check — SAM CLI's internal boto3 session still requires some region value to initialize. Fixed by scoping a placeholder `AWS_DEFAULT_REGION=us-east-1` around just that one call in `Invoke-OpenApiCheck`, restoring whatever value (or absence) existed before; this is not a deployment region decision, which remains WP-01's to make.
- Finding: four `npm --prefix web exec -- <tool> -- <args>` invocations (openapi-typescript generation, generated-file prettier formatting, `format`, `format-check`) each had a redundant second `--` between the tool name and its own arguments. `npm exec --` only needs one separator (npm's own flags vs. the command to run); a second literal `--` gets forwarded to the underlying tool as an argument. This was silently harmless for `openapi-typescript <path> --output <path>` (the next token was already positional) but broke `prettier -- --write <path>`: Prettier treated the leading `--` as "end of flags," so `--write`/`--check` were parsed as file glob patterns instead of flags, failing with "No files matching the pattern were found." Fixed by removing the redundant `--` in all four call sites. Not caught until the first real clean-clone run because the original development machine's npm resolved the malformed invocation differently, or the pinned `npm@12.0.2` behaves more strictly here than whatever was used while authoring Stage 3/4 — the exact prior mechanism is unconfirmed, but the fix (drop the stray separator) is unambiguous and verified against actual Prettier CLI parsing rules.
- Finding: after fixing `sam validate`'s missing-region failure, an audit of every other SAM CLI invocation found `sam local start-api` (used by both `dev` and `web-smoke`, directly and via `playwright.config.ts`'s `webServer`) has the identical exposure — it also initializes a boto3 session requiring some region even for fully local Lambda emulation. This had not yet failed because the original development machine apparently has some pre-existing AWS CLI/SDK configuration (from unrelated prior work) masking the gap; a genuinely fresh machine with zero `~/.aws/config` has none. Refactored the region-scoping logic out of `Invoke-OpenApiCheck` into a shared `Invoke-WithScopedAwsRegion` helper and applied it to `Invoke-Stage5Dev`'s and `Invoke-Stage5WebSmoke`'s SAM Local invocations too, rather than waiting for each to fail individually. General lesson: a bug's absence on the original authoring machine is not evidence of correctness when that machine carries undocumented ambient state (AWS config, PATH entries, cached tool installs); clean-clone evidence is the actual test, and once one instance of a bug class turns up, the fix should be searched for and applied everywhere that class of call exists, not just the one call site that happened to fail first.
- Finding: with the Docker credential-store issue fixed (unrelated stale `gcloud` `credHelpers` entries in the operator's `~/.docker/config.json`, from prior non-ProofPath work, breaking `docker.api.build`'s `get_all_credentials()` for every image regardless of registry), `sam local start-api` still failed the `web-smoke`/`dev` readiness wait on a genuinely cold host: it must pull/build the Lambda Runtime Interface Emulator base image on first invocation, which took longer than the existing 60-second timeout. This never surfaced on the original development machine because that image was already cached there from prior local testing. Bumped both `playwright.config.ts`'s SAM Local `webServer` timeout and `Invoke-Stage5Dev`'s equivalent `Wait-HttpReady` timeout from 60s to 180s to cover a genuine cold-cache first run.
- Finding: 180s was still insufficient on a genuinely cold host — SAM Local's first invocation both pulls the Lambda base image and builds a function image on top of it via `docker build`, which took longer than 3 minutes end-to-end on the operator's network. Progress output confirmed continuous forward progress, not a stall, so this was purely under-provisioned timeout, not a new defect. Bumped both timeouts to 600s (10 minutes). This is strictly a one-time cost per Docker image cache: once built, the image persists in the local Docker daemon and every subsequent invocation on that machine reuses it, so this only affects true first-run cold starts (a fresh clean-clone host, or a CI runner with no image cache).
- Decision: raised the same timeout to 1200s (20 minutes) per explicit user direction, to stop needing repeated timeout bumps across retries. Trade-off recorded here rather than silently accepted: a genuinely hung/broken `sam local start-api` (not just slow) would now take up to 20 minutes to fail instead of 3, which costs real GitHub Actions minutes on `web-smoke`/`dev`-adjacent CI runs if it ever does hang. Accepted because the observed behavior so far has always been slow-but-progressing, never a true hang.

## 2026-09-17 — WP-00 Stage 6 code-review follow-up

- Finding (code review, P4): the approved WP-00 spec listed three Stage 6 requirements that the initial implementation had not closed: `security` did not run the spec-mandated ignore-rule sentinel checks (AC-00-19's disposable-sentinel proof was only ever exercised manually, not by the `security`/Gate A command surface); no reviewable suppression mechanism existed despite AC-00-21 requiring one; and `.github/workflows/checks.yml`'s six jobs repeated identical checkout/setup blocks inline.
- Decision: added `Test-IgnoreSentinels` to `scripts/proofpath.ps1`, called from `Invoke-Stage6Security`, which creates disposable `FAKE-SENTINEL-DO-NOT-USE`-labelled files under representative `.gitignore` patterns (`.env.local`, `raw-audio/`, `private-evidence/`, `.aws-sam/build/`, `.tools/`), asserts each is ignored via `git check-ignore`, asserts `.env.example` and `web/.env.example` remain trackable, and always deletes every sentinel it created in a `finally` block so it never leaves stray files for `Assert-CleanTrackedTree`/`verify-gate-a` to trip over.
- Decision: added `security/suppressions.toml` as the reviewed suppression manifest AC-00-21 requires (tool, advisory/rule ID, narrow scope, reason, owner, approval, explicit ISO expiry per entry), starting empty. `Get-ActiveSuppressions` in `scripts/proofpath.ps1` parses it, fails the `security` command outright if any entry's `expires` date has passed, and translates non-expired `pip-audit` entries into `--ignore-vuln <id>` for both pip-audit invocations. Gitleaks and npm-audit entries in the manifest are reviewed documentation only — gitleaks has no narrow allowlist-file convention this script wires up, and npm 12's `npm audit` has no clean per-vulnerability CLI suppression flag — so a real finding from either still fails `security` until actually resolved; this limitation is documented in the manifest itself rather than faked with a mechanism that would not really suppress anything.
- Decision: extracted the repeated `actions/checkout` + `actions/setup-node` + `astral-sh/setup-uv` + optional `aws-actions/setup-sam` block from all six `.github/workflows/checks.yml` jobs into a new composite action, `.github/actions/setup-toolchain/action.yml`, parameterized by `full-history` (default `false`; only `security` sets it `true`, for Gitleaks) and `setup-sam` (default `false`; only `locks-and-generated`, `build`, and `web-smoke` set it `true`). Every pinned action reference/version was moved as-is, not changed, so each job's actual checkout depth and SAM CLI availability is unchanged from before.
- Finding (independent verification, P4): `Get-ActiveSuppressions` returned `$null` instead of an empty array when the suppression manifest has zero entries — a classic PowerShell gotcha where `return $emptyArray` unrolls to zero pipeline objects rather than one empty-array object. The actual `foreach` consumption in `Invoke-Stage6Security` tolerated this silently (iterating zero times), so it was not a live functional bug today, but any future caller expecting array semantics (`.Count`, indexing) would break. Fixed with the standard PowerShell idiom `return , $active` (unary comma forces the array through as a single pipeline object). Caught only by directly exercising the function after the code-review subagent's own test had already passed — a reminder that a subagent's "verified" claim is worth re-testing independently, not just re-reading.

## 2026-09-17 — WP-00 Stage 6 second code-review pass

- Finding (CRITICAL, caught by re-review): the `checks.yml` DRY refactor's composite action used `fetch-depth: ${{ inputs.full-history == 'true' && 0 || 1 }}`. Numeric `0` is falsy in GitHub Actions `&&`/`||` chains (same pitfall as JavaScript), so this expression always resolved to `1` regardless of `full-history` — silently regressing the `security` job's Gitleaks scan from full history to a 1-commit shallow checkout while the job kept reporting success, directly undermining AC-00-20. Fixed with `fetch-depth: ${{ fromJSON(inputs.full-history == 'true' && '0' || '1') }}` (string literals are truthy regardless of their text, so the falsy-0 trap never triggers; `fromJSON` casts the surviving string back to the integer `actions/checkout` expects). Verified by tracing GitHub Actions' documented falsy set (`false`, `0`, `''`, `null`) by hand for both branches before and after the fix, not just trusting the review's claim.
- Finding: `Test-IgnoreSentinels` created parent directories for nested sentinel paths (`raw-audio/`, `private-evidence/`) but never removed them, only the files — confirmed as *already having happened* in this repository (both directories existed as empty leftovers from an earlier verification run). Fixed by tracking only directories the function itself created (not pre-existing ones) and removing them in `finally` if left empty; leftover litter from the bug was deleted from the working tree.
- Finding: `Get-ActiveSuppressions`'s line regex could not parse a TOML value containing an escaped quote, and the `tool` field was accepted with no enum validation, so a typo (e.g. `"pip_audit"`) or a `gitleaks`/`npm-audit` entry would parse successfully yet silently enforce nothing, with no diagnostic. Fixed the regex to handle backslash-escaped characters (`(?:[^"\\]|\\.)*`) with a matching unescape step, added strict validation that `tool` is one of the three documented values (unknown values now throw), and made `gitleaks`/`npm-audit` entries print an explicit "documentation only, not enforced" notice so their limited enforcement is visible at run time, not just in a comment.
- Finding: the Gitleaks archive/checksums "skip re-download if cached" fix (previous entry) introduced a self-inflicted deadlock: a corrupted/truncated cached file would fail checksum verification forever, since nothing ever deleted the bad cache. Fixed by deleting the cached archive/checksums on a checksum mismatch, so the next invocation re-downloads instead of failing permanently. Also added a fast-path in `Install-Gitleaks` that skips the entire download/verify sequence when an already-installed binary already reports the correct version — closes the same redundant-work concern more completely, since `verify-clean-clone` calls `Install-Gitleaks` twice per run (via `setup` then `security`) and the second call is now near-instant instead of re-hashing/re-extracting.
- Finding: `Install-Gitleaks` and `Get-GitleaksInstallRoot` still independently recomputed the `.tools` root path after the earlier path-duplication fix only consolidated the install-root/binary-path helpers. Fixed by deriving `$toolRoot` in `Install-Gitleaks` from `Split-Path -Parent (Get-GitleaksInstallRoot)` instead of recomputing it.
- Also fixed two lower-severity items from the same pass: `Test-IgnoreSentinels` distinguishes `git check-ignore` exit code `1` (genuinely not ignored) from any other non-zero exit code (a fatal git error), instead of treating both identically; and removed a dead, always-empty `$output` variable capturing `--quiet` output that is never printed.
- Every fix above was independently re-verified by direct execution (not just re-reading the diff): re-ran `Test-IgnoreSentinels` and confirmed zero directory litter; isolated-tested the escaped-quote regex and the tool-typo rejection logic against synthetic input; confirmed `Install-Gitleaks`'s fast path actually prints its skip message on a second call; hand-traced the `fetch-depth` expression against GitHub Actions' documented truthy/falsy rules for both branches.

## 2026-09-17 — First real GitHub Actions run of checks.yml (WP-00 draft PR #1)

- Finding (CRITICAL, only visible on real CI, invisible in every prior review/local run): all six `checks.yml` jobs failed in 3-9 seconds with `Can't find 'action.yml', 'action.yaml' or 'Dockerfile' under '.../.github/actions/setup-toolchain'. Did you forget to run actions/checkout before running your local action?`. The Stage 6 DRY refactor moved `actions/checkout` *inside* the composite action itself (`.github/actions/setup-toolchain/action.yml`), and every job's first step was `uses: ./.github/actions/setup-toolchain`. A local composite action referenced by path cannot be resolved by the runner until the repository containing it is already checked out — so the action's own internal checkout step can never execute; nothing on the runner exists yet when the job tries to load the action file. This is a structural impossibility, not a flaky or environment-specific failure, and both code-review passes on Stage 6 (which caught the more subtle `fetch-depth` falsy-zero bug in this same action) missed it because neither pass executed the workflow for real.
- Fix: moved `actions/checkout` out of the composite action and into an explicit first step in every one of the six jobs in `checks.yml`. The composite action's `full-history` input was removed (no longer needed there); each job's checkout step now sets its own `fetch-depth` directly (`1` for five jobs, `0` for `security` to preserve Gitleaks' full-history scan) — this also removes the entire falsy-zero `fromJSON` workaround from the prior entry, since the ternary no longer needs to live inside the composite action's `with:` block.
- Lesson for future stages: a local composite/reusable workflow can never check out the repository it lives in as its own first action. Any composite action shared across jobs must assume checkout already happened, and every caller must checkout before invoking it — code review alone (reading the YAML) did not catch this; only an actual GitHub Actions execution did. Treat "the workflow file parses and the composite action file exists on disk" as insufficient proof that a workflow is correct.
